# Channels: Simplified Implementation Plan

**Goal:** Deliver one grounded pipeline response through Telegram and Microsoft Teams, with secure credentials, observable failures, history, and a meaningful test action.

**Depends on:** completed plans 01-04 and the Task 0 stabilization gate.

**Status:** Work 1-5 implementation is complete as of 2026-08-12. Automated verification and local platform demos pass; real Telegram and Teams tenant acceptance remains.

## Architecture

Adapters own platform protocol only. `ChannelHandler` owns the common workflow and calls `answer_question` once. The pipeline receives a `ChannelProfile` and returns final channel-safe text; adapters do not escape or format it again.

Persist channel credentials, status, recent error, last-success time, and most recent usable reply reference in the existing integration storage. Telegram uses long polling only. Teams uses one Bot Framework FastAPI endpoint.

## Work

### 1. Channel store and contracts

- Add Fernet credential encryption from `CREDENTIAL_ENCRYPTION_KEY`; reject a missing/invalid key and never persist plaintext.
- Define `InboundMessage(channel, user_ref, text, reply_ref)` and a small adapter protocol for normalize, typing, send, and profile.
- Store status, last success, last error, and last reply reference. Return credentials masked to last four characters.
- Test encryption at rest, undecryptable values, masking, and reply-reference round trips.

### 2. Shared handler and query log

- Handle text validation, typing indication, pipeline call, send, status update, and log append in one service.
- Continue after typing-indicator failure. Return a text-only message for unsupported input without running the pipeline.
- Measure end-to-end latency from accepted inbound message through send completion.
- Write query history after delivery; logging failure must not suppress the user reply.
- Test ordering and failures with fake adapters and a fake pipeline.

### 3. Telegram polling adapter

- Normalize captured `getUpdates` payloads, track offsets, send chat actions, and send the already formatted response.
- Use the small async `httpx` client with its SOCKS transport extra; do not add a Telegram framework or webhook endpoint.
- Reload the encrypted/environment credential between polls so token changes apply without restarting; reset the in-memory offset when the token changes.
- Honor standard HTTP proxy environment variables for networks where Telegram is not directly reachable.
- Run the poller in the FastAPI lifespan and cancel an outstanding long poll cleanly during shutdown.
- Test captured payloads, offsets, non-text input, API failures, and the 4096-character contract.

### 4. Teams adapter and endpoint

- Use `botbuilder-core` for authentication, activity normalization, typing, and replies.
- Mount one public messaging endpoint outside admin bearer authentication.
- Allow credential-free Bot Framework Emulator traffic only from loopback; non-local traffic requires configured Bot Framework credentials.
- Reload encrypted/environment Teams credentials for each inbound activity so later admin updates need no service restart.
- Test captured activities and authentication/failure behavior locally; use the Bot Framework Emulator only as an adapter check.

### 5. Integration API and acceptance

- Add authenticated list/save/clear/test operations under the shared `/admin` router.
- Return masked credential suffixes, setup state, connection status, last success/error, and whether a usable test destination exists; never return plaintext credentials or the reply reference.
- The test action uses the channel's last reply reference. Without one, report that a user must message the bot first.
- Report setup, credential, destination, pipeline, delivery, or complete stage and measured latency through actual delivery.
- Acceptance requires one real Telegram and one real Teams round trip. Record p50/p95 where enough samples exist; otherwise report each measured run and do not invent percentiles.

## Exit Gate

- Focused channel tests and the full suite pass.
- Stored credentials are demonstrably encrypted and never returned in plaintext.
- Both real platforms receive cited answers from at least two indexed documents.
- Delivery latency, connection status, and failures appear in the admin API.
