# Chat Channels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.
>
> **No implementation code in this plan.** Test expectations: `docs/superpowers/test-plans/05-channels-tests.md`.

**Goal:** Let users ask questions from Telegram and Microsoft Teams and get cited answers back, with admin-managed encrypted credentials, connection status, and an end-to-end test.

**Architecture:** Each adapter owns only its protocol — authentication, payload translation, delivery, typing indicators. Everything downstream sees a normalized message and knows nothing about the platform. Credentials are encrypted at rest and managed from the console.

**Tech Stack:** `httpx` (Telegram Bot API), `botbuilder-core` (Bot Framework), `cryptography` (Fernet), FastAPI

## Global Constraints

- Telegram runs long-polling by default — no public URL, no tunnel. Webhook mode is configurable.
- Teams must be operable against the Bot Framework Emulator with no Microsoft 365 tenant.
- Credentials Fernet-encrypted at rest; the API returns last-4 only; **a missing key fails startup rather than falling back to plaintext**.
- Round-trip target ≤3s; every query records measured latency.
- Adapter tests run against captured payloads — **no test contacts a live platform**.

### Task 1: Credential store

**Files:** Create `app/channels/credentials.py` · Test `tests/test_credentials.py`

**Interfaces:**
- Produces: `CredentialStore(engine, key: str)` with `save(channel, creds: dict)`, `load(channel) -> dict | None`, `masked(channel) -> dict`, `clear(channel)`; `CredentialError(Exception)`.

**Behaviour:**
- Credentials serialize to JSON and are Fernet-encrypted before persistence — one column covers Telegram's single token and Teams' id/password pair.
- **The raw database column must not contain the plaintext.** Assert that directly; it is the requirement, and an accidental plaintext write would otherwise pass every functional test.
- `masked` returns last-4 only; plaintext never crosses the API boundary.
- A missing or malformed key raises at construction — startup fails loudly, with **no plaintext fallback path** anywhere in the module.
- A credential that will not decrypt (key rotated away) raises `CredentialError` distinguishable from "not configured", so the channel can report "re-enter credential" instead of crashing.
- First-run fallback: no stored credential but a matching environment variable present uses that value and flags it as environment-sourced.

### Task 3: Telegram adapter

**Files:** Create `app/channels/telegram.py` · Test `tests/test_telegram_adapter.py`

**Behaviour:**
- Normalizes a captured `getUpdates` payload into `InboundMessage` with the correct chat id.
- Sends with MarkdownV2 escaping and enforces the 4096-character limit.
- Sends a typing action before model calls; **a typing failure never blocks the answer**.
- A payload with no text (sticker, photo) normalizes to `None`.
- Long-polling loop retrieves updates and acknowledges offsets so messages are not reprocessed.

### Task 4: Telegram webhook mode

**Files:** Create `app/api/telegram_webhook.py` · Test `tests/test_telegram_webhook.py`

**Behaviour:**
- Webhook endpoint verifies the configured secret token header; a wrong or missing token is rejected without processing.
- Registration on startup when webhook mode and a public base URL are configured; registration failure sets channel status disconnected with the reason.
- **Polling and webhook are mutually exclusive** — with polling active no webhook is registered, and a message is never processed twice.
